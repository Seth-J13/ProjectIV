# Behavior & Rules Reference

**Living snapshot** of product rules currently enforced by the app.

These files answer: _"What rules does the app enforce right now?"_  
They do **not** authorize new scope — implement only from `features/feature-*.md`.

| File                             | Role                                  |
| -------------------------------- | ------------------------------------- |
| [api.md](./api.md)               | Routes / payloads                     |
| [data-model.md](./data-model.md) | Tables / columns                      |
| **This file**                    | Ownership, sort, validation, UI rules |


| Rule                                                      | Enforcement                                                                                                                                                                                                                                                                                                                                                                                                 | Introduced                                                        |
| --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| Email and password sign-in                                | `POST /api/login` with Basic auth. Unknown email → **401** `User not found!`. Wrong password → **401** `Invalid password!`.                                                                                                                                                                                                                                                                                 | Feature 1                                                         |
| Create account                                            | First name, last name, email, and password are required. Role is `user`. Duplicate email → **409** `Email already in use!` and no new session.                                                                                                                                                                                                                                                              | Feature 1                                                         |
| Session lifetime                                          | Server session expires after 24 hours. Login reuses a non-expired session for that user before issuing a new token.                                                                                                                                                                                                                                                                                         | Feature 1                                                         |
| Logout                                                    | `POST /api/logout` deletes only the caller's current session, then the client clears `localStorage` `user` and returns to Login.                                                                                                                                                                                                                                                                            | Feature 1                                                         |
| Protected routes                                          | `authenticate` requires `Authorization: Bearer <session token>`. Missing or expired token → **401** and the handler does not run. The client clears `user` and returns to Login.                                                                                                                                                                                                                            | Feature 1                                                         |
| Signed-in screen                                          | `/landing` shows only `This feature has not been implemented yet` for every role.                                                                                                                                                                                                                                                                                                                           | Feature 1                                                         |
| Login screen                                              | Route `/` (`login`) keeps Email, Password, **Login** (`oc-cta`), and **Create Account**. Success stores the payload in `localStorage` `user` and shows snackbar `Login successful!` on email login.                                                                                                                                                                                                         | Feature 1                                                         |
| Continue with Google                                      | Secondary **Continue with Google** button. Email and Password are not required. The button uses `VITE_GOOGLE_CLIENT_ID` and Google Identity Services (`openid`, `email`, and `profile` only). The ID token is posted to `POST /api/google` and is not stored in `localStorage`.                                                                                                                             | Feature 2                                                         |
| Google system of record                                   | A new `googleSub` creates one user with role `user`, a null password, and the verified email and name. The app does not store a Google access token, refresh token, or password. Success JSON omits `password` and `googleSub`.                                                                                                                                                                             | Feature 2                                                         |
| Same Google account                                       | A later sign-in for the same `googleSub` does not insert a second user. Session create-or-reuse follows Feature 1.                                                                                                                                                                                                                                                                                          | Feature 2                                                         |
| Password account stays separate                           | Verified Google email that already belongs to a user with a password and no `googleSub` → **409** `Email already in use!`. That row is not changed and no session starts.                                                                                                                                                                                                                                   | Feature 2                                                         |
| Google-only account rejects password login                | Email/password login when `password` is null → **401** `Invalid password!`. No session starts.                                                                                                                                                                                                                                                                                                              | Feature 2                                                         |
| Google failure and cancel                                 | Missing ID token → **400** `Google sign-in failed.`. Invalid, expired, wrong-audience, or unverified token → **401** `Google sign-in failed.`. No given name or family name → **400** `Google did not provide a name.`. Cancel stays on Login with `Google sign-in was cancelled.` and no `user` in `localStorage`.                                                                                         | Feature 2                                                         |
| Google client secret                                      | `GOOGLE_CLIENT_SECRET` is read only on the server. It is not sent to the browser, included in API responses, or written to logs.                                                                                                                                                                                                                                                                            | Feature 2                                                         |
| Google session on protected routes                        | A Bearer token from `POST /api/google` authorizes protected routes the same way as an email/password session.                                                                                                                                                                                                                                                                                               | Feature 2                                                         |
| MenuBar                                                   | Signed-in initials, name, and email come from `localStorage` `user`. **Logout** ends that session and returns to Login. Hidden on the Login route. **Landing** is shown for every signed-in role and opens `/landing`. **User Management**, **Destinations**, **Drivers**, and **Areas** are shown only when `role` is `admin` and open `/users`, `/destinations`, and `/drivers`. **Vehicles** and **Maintenance** are shown when `role` is `admin` or `maintenance` and open `/vehicles` and `/maintenance-info`. | Feature 1, Feature 3, Feature 4, Feature 5, Feature 6, Feature 7, Feature 13 |
| User list                                                 | An admin on `/users` sees every account's first name, last name, email, and role, ordered by last name A–Z. Password, `googleSub`, and tokens are not shown.                                                                                                                                                                                                                                                | Feature 3                                                         |
| Edit user                                                 | **Edit** opens the current values. **Save** sends first name, last name, email, and role (`user`, `driver`, `maintenance`, or `admin`), stays on `/users`, and shows `User updated.`. **Cancel** closes the dialog without saving.                                                                                                                                                                          | Feature 3                                                         |
| Admin cannot change own role                              | Saving the signed-in admin with a different role → **400** `You cannot change your own role.` The role stays `admin`. The same admin may still change their own name and email.                                                                                                                                                                                                                             | Feature 3                                                         |
| Duplicate email on edit                                   | Saving an email that belongs to a different user → **409** `Email already in use!`. That user is unchanged.                                                                                                                                                                                                                                                                                                 | Feature 3                                                         |
| Non-admin user management                                 | Roles `user`, `driver`, and `maintenance` do not see **User Management**. Opening `/users` redirects to `/landing`. User APIs return **403** `Admin access required.` and do not return or change rows.                                                                                                                                                                                                     | Feature 3                                                         |
| Unknown user                                              | `PUT /api/users/:id` for a missing id → **404** `User with id={id} not found.`                                                                                                                                                                                                                                                                                                                              | Feature 3                                                         |
| Email change keeps the session                            | Updating a user's email writes the new email onto that user's session rows and does not replace the token.                                                                                                                                                                                                                                                                                                  | Feature 3                                                         |
| Vehicle page access                                       | `/vehicles` (`vehicleManagement`) is limited to `admin` and `maintenance`. Other signed-in roles are sent to `/landing`. Vehicle APIs for other roles return **401** `Unauthorized user`.                                                                                                                                                                                                                   | Feature 4                                                         |
| Vehicle ownership                                         | Vehicles are not owned by a user. Any `admin` or `maintenance` session may list, create, update, and delete any vehicle.                                                                                                                                                                                                                                                                                    | Feature 4                                                         |
| Vehicle create verbs                                      | Creating a vehicle uses `PUT /api/vehicle-t3/vehicles/`. Updating uses `POST /api/vehicle-t3/vehicles/:vin`.                                                                                                                                                                                                                                                                                                | Feature 4                                                         |
| Vehicle client validation                                 | Invalid Add/Edit Vehicle form input shows `An error occured processing your form.` and does not call the API.                                                                                                                                                                                                                                                                                               | Feature 4                                                         |
| New maintenance info / fuel type confirm                  | Adding a vehicle with a new make/model/year opens **Confirm Add New Maintenance Info?**. A new fuel type opens **Confirm Add New Fuel Type?**. Cancel returns to the Add/Edit modal with no API call. Confirm creates fuel (when needed), then maintenance info, then the vehicle.                                                                                                                          | Feature 4                                                         |
| Vehicle list filters                                      | Year, Make, Model, Color, Area, License, From Purchase Date, and Before Purchase Date filter the loaded vehicle list on the client as values change.                                                                                                                                                                                                                                                        | Feature 4                                                         |
| Maintenance navigation                                    | The Maintenance action on a vehicle row opens route `maintenance` with that vehicle's VIN in the path and does not send an API request.                                                                                                                                                                                                                                                                     | Feature 4                                                         |
| Maintenance page access                                   | `/maintenance-info/:vin?` (`maintenance`) is limited to `admin` and `maintenance`.                                                                                                                                                                                                                                                                                                                          | Feature 5                                                         |
| Maintenance notes                                         | Notes belong to a request for the selected vehicle. Add/edit validate subject and description (max 255). Completing a note creates a vehicle service log, then deletes the note.                                                                                                                                                                                                                            | Feature 5                                                         |
| Mileage update                                            | Update Mileage requires a whole number greater than the current mileage, then `PUT /api/vehicle-t3/vehicles/:vin`.                                                                                                                                                                                                                                                                                          | Feature 5                                                         |
| Fuel management                                           | Manage Fuels can add, edit, and delete fuel types used by maintenance info.                                                                                                                                                                                                                                                                                                                                 | Feature 5                                                         |
| Service logs / Back | **View Service Logs** on a vehicle's maintenance page opens the **Vehicle Service Logs** modal for that VIN. It does not change the route. **Back** returns to `vehicleManagement`. | Feature 5, Feature 10 |
| Vehicle log access | `maintenance` and `admin` may list and create logs. `user` and `driver` receive **403** `Forbidden` and do not see the log list. Opening `/vehicle-logs` sends those roles to `/landing`. | Feature 10 |
| Vehicle log writes | The creator is stored as `creatorId` and as the first owner. An owner or an `admin` may update the description and completed status, and may add or remove another owner. Only the creator or an `admin` may change the service date or vehicle, or delete the log. An added owner who changes the service date or vehicle, or who deletes the log, receives **403** `Forbidden` and those values stay. On the open log, **Service date** and **Vehicle** are gray and read-only for anyone else, and hovering either field shows **Only the original owner and admins can modify this field.** **Delete** asks **Delete this vehicle service log?** and leaves the log until that is confirmed. A missing field is **400** `Vehicle log is incomplete!`. An unknown vin is **404** `Vehicle not found!`. Clicking outside the create or edit dialog closes it and discards unsaved changes, including an owner added or removed in that dialog. | Feature 10 |
| Vehicle log owner picker | The log list and the open log show every saved owner. **User** is a combobox like driver id: rows are `Name (id)`, typing filters the name and the id. **Add owner** puts that person on the list in the dialog, and **Save** sends `{ "userId": <id> }` only. Another owner is added beside the ones already stored. **Remove** takes that person off the list in the dialog, and **Save** deletes that person. Clicking outside discards an owner added or removed in that dialog. Choices come from `GET /api/vehicle-logs/owner-choices` and include only `id`, `firstName`, and `lastName`. | Feature 10 |
| Vehicle log retention | A log whose service date is more than 18 months ago is deleted when logs are listed or read and no longer appears for that vehicle. | Feature 10 |
| Destination list                           | The admin menu bar has a **Destinations** button that opens `/destinations`. An admin on `/destinations` sees **Manage Destinations**. Any other signed-in role is sent to the landing page (`home` when that route exists). Rows show name, street address, address line 2 (blank when null), city, state, zip, and visited date. An empty `last_visited` shows `not visited`.                                                                                                                                                                        | Feature 6                                  |
| Destination batches and sort               | The list loads at most 5 destinations at a time and appends the next batch at the bottom of the page. Default order is the most recent `last_visited_on`, with null or future dates after visited rows. Name, city, state, and zip can be sorted ascending or descending.                                                                                                                                                                                                 | Feature 6                                  |
| Destination search                         | The search field and attribute select are hidden when no destinations are loaded. With no attribute selected, the query matches `dest_name`. **City**, **State**, **Zip Code**, **Street Address**, and **Address Line 2** match those columns.                                                                                                                                                                                                                           | Feature 6                                  |
| Destination form                           | **+ New Destination** opens **Add Destination**. **Edit** opens **Edit Destination** with that row's values. **Cancel** or a click outside clears the fields and closes the form. **Add** and **Save** stay open when a field is empty or the zip is not `#####` or `#####-####`. Empty required fields show `Required` and `Missing fields: ` plus the field names. Zip entry keeps digits only and inserts a hyphen after the fifth digit. Address line 2 may be empty. | Feature 6                                  |
| Destination writes                         | Create and update send `dest_name`, `addr_line_1`, `addr_line_2`, `city`, `state`, and `zip`. A successful create or update shows the response message, reloads the list, and removes that message after 3 seconds. **Delete** asks in **Delete Destination**; **Cancel** or a click outside does not delete. Confirming delete shows `Successfully deleted Destination!` and reloads the list.                                                                           | Feature 6                                  |
| Destination access                         | Any signed-in user may list, read, and create destinations. Only an admin may update or delete. Destinations are not owned by a user, and responses do not include user fields. The same address (`zip`, `city`, `state`, `addr_line_1`, `addr_line_2`) cannot be stored twice.                                                                                                                                                                                           | Feature 6                                  |
| Driver reads require a session                            | `GET /api/vehicle-t3` returns `401` without a bearer token                                                                                                                                                                                                                                                                                                                                                  | Feature 7                                                         |
| Only admins create, update, or delete drivers             | Non-admin writes return `403` `{ "message": "Admin access required." }`. Drivers are not owned by a user                                                                                                                                                                                                                                                                                                    | Feature 7                                                         |
| Driver id must be an integer                              | Non-numeric `driver_id` returns `400`                                                                                                                                                                                                                                                                                                                                                                       | Feature 7                                                         |
| License status, expiration, and availability are required | Missing or blank values return `400`. Status and availability are single-select dropdowns of the allowed enum values                                                                                                                                                                                                                                                                                        | Feature 7                                                         |
| A blank driver name is rejected                           | Whitespace-only `name` returns `400`. The drivers form blocks it before the request                                                                                                                                                                                                                                                                                                                         | Feature 7                                                         |
| Driver id choices                                         | **Driver id** sits above **Driver name**. The list shows each user as `First Last (id)`. Choosing one stores only the id, fills **Driver name**, and keeps that name read-only until the id is cleared                                                                                                                                                                                                      | Feature 7                                                         |
| Drivers screen is admin-only                              | Signed-out users go to login. Signed-in non-admins go to `/landing`                                                                                                                                                                                                                                                                                                                                         | Feature 7                                                         |
| Request routes require a session | Missing bearer token on `/api/requests` returns `401` `{ "message": "Unauthorized!" }` | Feature 8 |
| Request owner | `requesterId` is the signed-in user. A client-supplied id is ignored | Feature 8 |
| Trip schedule | Start and end times may be empty. An end date before the start date returns `400` `{ "message": "end must be after start." }`. The same day is allowed. When both times are present on that day, the end time must be later than the start time. A later end date is allowed even when the clock time is earlier or either time is empty. A trip requires an end date. A maintenance request may omit the end date. `numPeople` below 1 returns `400` `{ "message": "number of people must be at least 1." }` | Feature 8 |
| Request references | An unknown vehicle returns `400` `{ "message": "vehicle does not exist." }` | Feature 8 |
| Maintenance requests | An `admin` or `maintenance` user can create `maintenance`. A `user` or `driver` receives `403` `{ "message": "Admin access required." }` | Feature 8 |
| Request activity | `currentlyActive` is `true` only when the start is before now and, if an end date exists, the end is after now. An earlier or later date ignores the clock time. On today's date, the start time must be before now and the end time must be after now. A missing end date leaves that half unchecked. The request list's first load, and turning **Active only** on, recalculates the flag for every listed request | Feature 8 |
| Request visibility | A `user` or `driver` sees and changes only their own requests. Another user's id is `404`. An admin sees and can edit every request. A `maintenance` user lists their own requests plus every `maintenance` request, but can change only their own | Feature 8, Feature 12 |
| Requests screen | Signed-out users opening `requests` go to login | Feature 8 |
| Vehicle in use | A vehicle is in use while any request for it has a start before now and no end, or an end after now. `GET /api/vehicles` returns this as `inUse`. A vehicle booked for a later date stays available until the start | Feature 12 |
| Landing lists | **Available Vehicles** (every role): `available` and not in use. **Your Reserved Vehicles** (every role): vehicles with an in-use request whose `requesterId` is the signed-in user. **Vehicles In Service** (`admin`, `maintenance`): vehicles with an in-use `maintenance` request. **Reserved Vehicles** (`admin`): vehicles with any in-use request. A vehicle appears once per list. The `Image` column shows a placeholder until vehicle images exist | Feature 12 |
| Landing navigation | Clicking an available vehicle fills the request form vehicle and sends no API request. Clicking a reserved vehicle opens `requests` with `?vehicleId=`. Clicking an in-service row or its **Info** button opens `maintenance` for that VIN. **Info** on a reserved vehicle opens `requests` with `?vehicleId=` | Feature 12 |
| Landing request forms | Every role sees the trip form. `admin` and `maintenance` get a switch (**Request** / **Maintenance**) that swaps in the maintenance form with no API request. Submit always sends `POST /api/requests`. A `201` clears the form and reloads the lists. A `400` shows the server `message` and keeps the entries | Feature 12 |
